Slide 05 · split

Preconditions: Client Obligations

Apply
Bloom evidence: Students trace buggy Stack.pop() code to identify precondition violations, locate the bug in caller code, and analyze why defensive checks mask rather than fix contract violations—apply-level debugging.
text

Preconditions define valid states for calling a routine—constraints on arguments and object state that the CLIENT must ensure. **Key Principle:** Client responsibility to ensure; supplier right to assume (no defensive checks). Violations indicate bugs in the caller.

code
class Stack<T> {
  // Precondition: !isEmpty()
  public T pop() {
    // No check needed—caller's job!
    return items[--size];
  }
}

// CLIENT CODE:
if (!stack.isEmpty()) {
  item = stack.pop(); // Valid
}
stack.pop(); // BUG: violates precondition
activity

Activity: Apply: Trace Responsibility

Speaker notes

This apply-level activity moves beyond explaining preconditions to analyzing buggy code through the DbC lens. Expected answers: Line with bare pop() violates precondition; bug is in caller (failed to check); fix by adding isEmpty() guard. Key insight: defensive checks in pop() hide the caller's bug—it still violates the contract, just doesn't crash. This reinforces that preconditions shift responsibility and enable fail-fast at the true bug source. Poll students on the defensive check question to surface the common misconception that exception handling fixes contract violations. Connects to slide 4's DbC vs. defensive programming comparison.

Writing Effective Preconditions

Evaluate
Bloom evidence: Students evaluate three precondition options (A/B/C) for Account.withdraw() using four criteria (precise, complete, minimal, pure) and justify the best choice considering reusability vs. correctness—evaluate-level design judgment.
bullets
  • Precise: boolean expressions, not prose (x > 0, not 'x is positive')
  • Complete: cover all constraints (nulls, boundaries, state)
  • Minimal: weakest condition that ensures correctness
  • Pure: no side effects in contract expressions
code
class Account {
    private double balance;
    
    // EVALUATE: Which precondition is best?
    // A: require balance >= amount
    // B: require amount > 0 && balance >= amount
    // C: require amount > 0 && amount <= 1000 && balance >= amount
    public void withdraw(double amount) { ... }
}
activity

Activity: Evaluate & Justify (4 min)

Instructions: Individually: Choose the best precondition (A/B/C) and write 2-3 sentence justification using the four criteria above. Then pair up: Compare choices. If you disagree, debate using criteria—is one over-specified? Missing constraints? Does it enable maximum reusability while ensuring correctness? Prepare to defend your choice to the class.

Speaker notes

This evaluate-level activity requires students to apply all four criteria simultaneously and make a justified design decision. Expected answer: B is best. A is incomplete (missing amount > 0 allows negative withdrawals). C is over-specified (arbitrary 1000 limit reduces reusability without correctness benefit). During debrief, emphasize trade-offs: stronger preconditions are easier to implement but limit clients. Weaker preconditions increase reusability but may require more complex implementations. This bridges to postconditions next slide and supports the apply-level objective for writing contracts.

Postconditions: Supplier Guarantees

Analyze
Bloom evidence: Students identify missing guarantees in transfer() postcondition, trace how preconditions propagate through withdraw() calls, and analyze contract composition—analyze-level completeness debugging and compositional reasoning.
text

**Postconditions** specify guarantees about return values and state changes—what the supplier promises if preconditions are met. **Key principle:** Client relies on postcondition without inspecting code. Violations indicate implementation bugs.

code
// require: amount > 0 && balance >= amount
// ensure: balance == old(balance) - amount
public void withdraw(double amount)

// require: !isEmpty()
// ensure: size() == old(size()) - 1 && returns old(first())
public T removeFirst()

// INCOMPLETE SPECIFICATION - what's missing?
// require: src != null && dest != null
// ensure: dest.balance == old(dest.balance) + amount
public void transfer(Account src, Account dest, double amount) {
    src.withdraw(amount);  // calls contracted method
    dest.deposit(amount);  // calls contracted method
}
activity

Activity: Analyze: Debug Contract Completeness (6 min)

Instructions: The transfer() postcondition is incomplete. Working in pairs: (1) Identify ALL missing guarantees (what about src.balance? return values from withdraw/deposit? edge cases?). (2) Trace how transfer's precondition must strengthen to satisfy withdraw's precondition—what constraint propagates? (3) Write the complete, minimal postcondition. Deliverable: List of missing guarantees + corrected specification. Be ready to explain how contracts compose through method calls.

Speaker notes

This slide elevates from apply to analyze by introducing contract composition and completeness debugging. The transfer() example requires students to trace precondition propagation (transfer must ensure src.balance >= amount to satisfy withdraw's precondition) and identify missing postcondition guarantees (src balance change, both method success, no exception thrown). This addresses two identified gaps: multi-method contract reasoning and contract completeness analysis. During debrief, emphasize that calling contracted methods creates obligations—the caller's precondition must imply the callee's. Common mistakes: forgetting source account state change, not considering exception cases. This prepares students for 'old' keyword mechanics in slide 9 while building compositional reasoning skills.

Slide 12 · split

Invariant Preservation Analysis

Create
Bloom evidence: Students trace invariant preservation through dequeue/enqueue sequence, then design replace() method by composing existing contracts, discovering that it inherits both preconditions—create-level contract synthesis through composition.
code
class BoundedQueue<T> {
  private T[] items;
  private int head, tail, count, capacity;
  // INV: 0 <= count <= capacity
  // INV: 0 <= head, tail < capacity
  // INV: count == actual items stored
  
  public void enqueue(T item) {
    // PRE: count < capacity
    items[tail] = item;
    tail = (tail + 1) % capacity;
    count++;
    // POST: count == old(count) + 1
  }
  
  public T dequeue() {
    // PRE: count > 0
    T result = items[head];
    head = (head + 1) % capacity;
    count--;
    return result;
    // POST: count == old(count) - 1
  }
}
activity

Activity: Multi-Method Contract Composition

Speaker notes

This elevated activity addresses two gaps: multi-method contract reasoning and invariant design practice. Students must trace contract composition across method boundaries—analyzing how dequeue's postcondition enables enqueue's precondition. The replace() design task raises cognitive demand to create-level: students synthesize a new contract by composing existing ones, discovering that replace() inherits dequeue's precondition (count > 0) AND enqueue's precondition (count < capacity), requiring count >= 1. During debrief, ask: 'Can replace() have weaker preconditions than calling dequeue+enqueue separately?' This reveals how contract composition constrains design and connects invariant preservation to method orchestration, supporting both 'write invariants' and 'apply DbC principles' objectives.

The Liskov Substitution Principle

Analyze

heading

Behavioral Subtyping Through Contracts

quote

Objects of a subtype must be substitutable for objects of the supertype without breaking program correctness.

bullets
  • Structural compatibility ≠ behavioral compatibility
  • Contracts formalize LSP: subtypes honor supertype obligations
  • Violation breaks polymorphism and client assumptions
activity

Activity: Identify LSP Violations

Instructions: Analyze three inheritance examples: (1) Square extends Rectangle with setWidth() setting both dimensions; (2) ReadOnlyList extends List but throws exception on add(); (3) SortedSet extends Set ensuring iteration order. For each: Does it violate LSP? Why or why not? Which client expectations break? How would contracts expose the violation?

Speaker notes

This analyze-level activity targets the 'Apply contract inheritance rules and understand behavioral subtyping' objective. Students must evaluate whether inheritance hierarchies preserve substitutability by reasoning about behavioral expectations. Square/Rectangle violates LSP because clients expect independent width/height modification—contracts would show postcondition violation. ReadOnlyList clearly violates by strengthening preconditions (add() now requires false). SortedSet doesn't violate LSP—it strengthens postconditions (adds ordering guarantee) which is safe. Guide discussion to connect violations with contract rules from next slide, showing how weakening/strengthening rules prevent these problems.

Contract Inheritance Rules

Create

bullets
  • Preconditions: may only WEAKEN (require less)
  • Postconditions: may only STRENGTHEN (promise more)

  // ensure: area >= 0
  double area() {...}
}

class Circle extends Shape {
  // require: true (same - OK)
  // ensure: area >= 0 && area == PI*r*r (stronger - OK)
  double area() {...}
}

This create/analyze activity addresses multiple gaps: designing complete contracted classes, analyzing contract composition through call chains, and applying inheritance rules.
