What is Requirements Engineering?

text

**Requirements Engineering**: Systematic process of defining, documenting, and maintaining software requirements **Key Impact**: 60-70% of software failures trace to requirements issues **Core Challenge**: Bridge between stakeholder needs and system implementation

activity
  • A. The system must process 10,000 transactions per second
  • B. The system must use Apache Kafka for messaging
  • C. Users must receive order confirmation within 2 seconds
  • D. The system should be user-friendly and fast
  • E. The application must support accessibility features
Speaker notes

Present the definition emphasizing the problem-solution bridge. The activity now requires evaluate-level thinking: students must judge quality against multiple criteria (testability, specificity, problem-focus), then synthesize corrections. Walk through examples highlighting that even statement E, which sounds like a requirement, fails specificity tests. Discuss how B might be valid if it's a genuine stakeholder constraint, but usually reflects premature design. Connect to real failures where vague requirements like D caused project disputes. This evaluation skill is foundational for all subsequent RE stages—students must recognize quality issues before learning elicitation and documentation techniques.

Writing Quality Requirements

Evaluate
Bloom evidence: Activity requires evaluating three requirement versions, identifying conflicting quality characteristics, and recommending best version with risk assessment—judging trade-offs between competing valid approaches.
bullets
  • Modal verbs: 'shall' (mandatory), 'should' (desirable), 'may' (optional)
  • Avoid ambiguous terms without quantification
  • One requirement per statement (atomic)
  • Each requirement must be verifiable
code
❌ Poor: 'The system should be secure and easy to use'

✓ Good: 'The system shall require authentication using 
   username and password before accessing user data'

❌ Poor: 'The system will handle lots of users'

✓ Good: 'The system shall support 10,000 concurrent 
   users with response time < 3 seconds'
activity

Activity: Evaluate: Requirements Quality Trade-offs

Speaker notes

This activity elevates the slide to evaluate level by requiring students to assess competing requirement formulations rather than just fixing defects. After individual analysis, facilitate discussion: Why might Version A fail feasibility review despite being specific? How does domain (healthcare) influence which version is appropriate? What validation methods would catch issues in each version? This bridges to slide 12's use cases by showing that good requirements balance multiple quality dimensions. The trade-off analysis prepares students for real-world scenarios where perfect requirements are impossible and stakeholder negotiation is necessary.

Best Practices and Common Pitfalls

Understand

Best Practices

bullets
  • Involve stakeholders early and continuously
  • Use multiple elicitation techniques for triangulation
  • Validate requirements before implementation
  • Maintain traceability for impact analysis
text

Common Pitfalls

bullets
  • Gold plating: Unnecessary features → Strict prioritization
  • Scope creep: Uncontrolled additions → Change control
  • Ambiguous requirements: Unclear specs → Structured templates
  • Insufficient validation: Assumed correctness → Systematic reviews
Speaker notes

Synthesize key lessons. Best practices: stakeholder involvement prevents misunderstandings, multiple techniques catch more requirements, early validation prevents costly rework, traceability supports change management. Common pitfalls with mitigations: gold plating (building unnecessary features) - use strict prioritization; scope creep (uncontrolled additions) - enforce change control; ambiguity (unclear specs) - use templates and reviews; insufficient validation (assuming correctness) - implement systematic validation. Share success story: agile project reduced rework 40% through incremental requirements refinement.
