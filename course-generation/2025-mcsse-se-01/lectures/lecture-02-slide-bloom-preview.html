Multiple Inheritance: Power and Complexity

Understand
Bloom evidence: Introduces MI concepts, DAG structures, and language support differences—explanatory content without application activities on this slide.
bullets
  • Inherit from multiple parent classes
  • Combine orthogonal features (mixins)
  • Creates DAG (Directed Acyclic Graph) structures
  • Supported: C++, Eiffel, Python
  • Not supported: Java, C# (use interfaces instead)
Speaker notes

Multiple inheritance is powerful but complex. It allows combining features from multiple sources—useful for mixins or when an object genuinely has multiple roles. Emphasize the structural difference: no longer a tree, but a DAG. Many languages avoid it due to complexity; Java/C# use single inheritance + interfaces as a compromise.

Slide 08 · code

Resolving the Diamond: Eiffel Approach

Understand
Bloom evidence: Demonstrates Eiffel's rename solution with code example and explains trade-offs—explanatory rather than requiring students to implement or evaluate.
code
class TEACHING_ASSISTANT
inherit
    STUDENT
        rename
            id as student_id
        end
    EMPLOYEE
        rename
            id as employee_id
        end
feature
    student_id: STRING
    employee_id: STRING
    
    -- Now both IDs are accessible
    -- No ambiguity
end
Speaker notes

Eiffel's solution: explicit renaming. The programmer must decide how to handle conflicts. Here we rename both 'id' attributes to make them distinct. Alternative: use 'select' to choose one. This makes the programmer's intent clear and prevents silent errors. Discuss trade-off: more verbose but safer.

Polymorphism: One Interface, Many Forms

Understand
Bloom evidence: Explains polymorphism concept with memory diagram showing static vs. dynamic types—conceptual explanation without application task.
bullets
  • Single interface, multiple implementations
  • Subtype polymorphism (inheritance-based)
  • Write code that works with any subtype
  • Enables extensibility without modification
diagram

Prompt: Memory diagram showing an array labeled 'shapes: ARRAY[SHAPE]' containing references pointing to different objects: a Circle object, a Rectangle object, and a Triangle object. Show the array holding references (arrows) to these different concrete types. Label static type as SHAPE and dynamic types as Circle, Rectangle, Triangle.

Speaker notes

Polymorphism is the ability to treat objects of different types uniformly through a common interface. The array has static type ARRAY[SHAPE], but contains objects of dynamic types Circle, Rectangle, Triangle. This is the power of polymorphism: write code once (iterate over shapes), works with any shape type, including types not yet invented.

Slide 11 · content

Liskov Substitution Principle (LSP)

Understand
Bloom evidence: Defines LSP, explains behavioral subtyping and contract rules—conceptual understanding with Square/Rectangle example but no application activity.
quote

Objects of a subtype should be substitutable for objects of the supertype without altering program correctness.

bullets
  • Behavioral subtyping, not just structural
  • Preserve invariants and contracts
  • Weaken preconditions, strengthen postconditions
  • Violations lead to subtle bugs
Speaker notes

LSP is crucial for correct inheritance. It's not enough that a Square IS-A Rectangle structurally—it must behave correctly in all contexts where Rectangle is used. Classic violation: if Rectangle has setWidth/setHeight that work independently, but Square must keep width=height, substituting Square breaks code expecting Rectangle behavior. Always think: can I use the child wherever the parent is expected?

Slide 12 · code

Polymorphism in Eiffel

Understand
Bloom evidence: Shows polymorphic code example (zoo feeding) with explanation of dynamic dispatch—students read and comprehend code rather than write it.
code
class ZOO
feature
    animals: LINKED_LIST[ANIMAL]
    
    feed_all
        local
            animal: ANIMAL
        do
            from animals.start
            until animals.after
            loop
                animal := animals.item
                animal.eat  -- Polymorphic call
                animals.forth
            end
        end
end

-- Works with Dog, Cat, Bird, etc.
-- Each implements 'eat' differently
Speaker notes

This demonstrates polymorphic programming. The feed_all method works with any ANIMAL subtype. The call to animal.eat is polymorphic—which implementation runs depends on the dynamic type (Dog.eat, Cat.eat, etc.). Note that static type is ANIMAL, but dynamic type varies. This is resolved at runtime through dynamic binding, our next topic.

Slide 13 · content

Dynamic Binding: Runtime Method Resolution

Understand
Bloom evidence: Explains static vs. dynamic binding, vtable mechanism, and trade-offs—conceptual explanation of the mechanism.
bullets
  • Static binding: resolved at compile time
  • Dynamic binding: resolved at runtime
  • Enables polymorphism to work
  • Uses virtual method table (vtable)
  • Trade-off: flexibility vs. performance
Speaker notes

Dynamic binding is the mechanism that makes polymorphism work. When you call animal.eat, the compiler doesn't know which eat method to call—it depends on the runtime type. Dynamic binding defers this decision to runtime using a vtable. This adds a small performance cost (indirection) but gives enormous flexibility. In Eiffel, all calls are dynamically bound by default.

Slide 14 · split

Virtual Method Table (vtable)

Understand
Bloom evidence: Detailed explanation of vtable implementation with memory diagram showing lookup process—understanding the mechanism rather than analyzing performance or implementing.
diagram

Prompt: Detailed memory layout diagram showing: 1) A Dog object in memory with a vtable pointer at the top, followed by data fields. 2) The vtable pointer (arrow) pointing to Dog's vtable. 3) Dog's vtable as a table with entries: eat -> Dog.eat, sleep -> Dog.sleep, speak -> Dog.speak. 4) Show similar structure for Cat object pointing to Cat's vtable. Label clearly: 'vtable pointer', 'Dog vtable', 'method addresses'.

bullets
  • Each object has vtable pointer
  • Vtable maps method names to addresses
  • Runtime: follow pointer, lookup method, call
  • One vtable per class, shared by all instances
Speaker notes

This is how dynamic binding works under the hood. Each object has a hidden pointer to its class's vtable. When you call animal.eat: (1) follow the vtable pointer, (2) look up 'eat' in the table, (3) call the address found. This is fast (two indirections) but slower than static calls. One vtable per class, not per object, so memory overhead is minimal.

Method Redefinition: Apply It

Apply
Bloom evidence: Students design RECTANGLE and TRIANGLE classes with redefined area methods, deciding on features and implementations—hands-on application of redefinition.
code
class SHAPE
feature
    area: REAL
        deferred
        end
end

class CIRCLE
inherit
    SHAPE
        redefine area end
feature
    radius: REAL
    area: REAL
        do
            Result := 3.14159 * radius * radius
        end
end
activity
Speaker notes

Students now apply redefinition to new shapes. Walk through CIRCLE first: deferred means no implementation in parent; redefine clause signals override; effective implementation required. Then give 3 minutes for the activity. Circulate and check designs. Common solution: RECTANGLE needs width, height; area = width * height. TRIANGLE needs base, height; area = 0.5 * base * height. Some may suggest adding perimeter as deferred. Debrief 2-3 solutions, emphasizing the redefine clause and that each subclass provides appropriate calculations.

Using Precursor: Extending Parent Behavior

Understand
Bloom evidence: Demonstrates Precursor usage in MANAGER.calculate_salary example—shows how to extend behavior but students don't implement it themselves on this slide.
code
class EMPLOYEE
feature
    calculate_salary: REAL
        do
            Result := base_salary
        end
end

class MANAGER
inherit
    EMPLOYEE
        redefine calculate_salary end
feature
    calculate_salary: REAL
        do
            Result := Precursor + bonus
            -- Calls EMPLOYEE.calculate_salary
            -- then adds bonus
        end
end
Speaker notes

Precursor calls the parent's implementation. This is crucial for extending rather than replacing behavior. MANAGER.calculate_salary builds on EMPLOYEE.calculate_salary by adding a bonus. This promotes code reuse and maintains the parent's logic. Without Precursor, you'd have to duplicate the base_salary calculation. Similar to 'super' in Java or Python.

Design Patterns: Template Method

Understand
Bloom evidence: Explains Template Method pattern with UML diagram and describes how it leverages inheritance—conceptual understanding of pattern structure.
diagram

Prompt: UML class diagram showing Template Method pattern. Abstract class DataProcessor at top with template method 'process()' that calls abstract methods 'read_data()', 'process_data()', 'write_data()'. Two concrete classes below: CSVProcessor and JSONProcessor, each implementing the three abstract methods. Show the sequence: process() calls the three steps in order.

bullets
  • Define algorithm skeleton in parent
  • Subclasses customize specific steps
  • Parent controls overall flow
  • Promotes consistency and reuse
Speaker notes

Template Method is a classic pattern leveraging inheritance and redefinition. The parent defines the algorithm structure (process = read, then process, then write), but leaves specific steps abstract. Each subclass provides concrete implementations. This ensures all processors follow the same flow while allowing customization. Common in frameworks. Note how this relies on dynamic binding to call the right implementations.

Common Pitfalls and Best Practices

Remember
Bloom evidence: Lists best practices and pitfalls to avoid—primarily recall of guidelines without application or evaluation activities.
bullets
  • Avoid deep hierarchies (> 4-5 levels)
  • Favor composition over inheritance for 'has-a'
  • Don't break encapsulation with protected members
  • Ensure LSP compliance—test substitutability
  • Document redefinable methods clearly
Speaker notes

Common mistakes: deep hierarchies become hard to understand (yo-yo problem). Use composition when objects have parts, not when they are subtypes. Protected members can break encapsulation—prefer private with protected accessors. Always test that subclasses can substitute for parents. These practices prevent the 'fragile base class' problem where changes to parents break children.
