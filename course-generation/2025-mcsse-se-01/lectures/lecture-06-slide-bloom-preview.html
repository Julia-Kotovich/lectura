Strategy Pattern: Before and After

Understand
Bloom evidence: Shows refactoring example demonstrating Strategy benefits, primarily for understanding pattern advantages
code
// BEFORE: Conditional logic
class PaymentProcessor {
    void processPayment(String type, double amount) {
        if (type.equals("CREDIT")) {
            // Credit card logic
        } else if (type.equals("PAYPAL")) {
            // PayPal logic
        } else if (type.equals("BITCOIN")) {
            // Bitcoin logic
        }
    }
}

// AFTER: Strategy pattern
interface PaymentStrategy {
    void pay(double amount);
}

class PaymentProcessor {
    private PaymentStrategy strategy;
    
    void setStrategy(PaymentStrategy strategy) {
        this.strategy = strategy;
    }
    
    void processPayment(double amount) {
        strategy.pay(amount);  // Clean delegation
    }
}
Speaker notes

This before-and-after comparison shows Strategy's power. The before version has growing conditional complexity - every new payment method requires modifying this class. The after version uses composition and polymorphism. Adding a new payment method just means creating a new strategy class - no modification to existing code. This follows the Open-Closed Principle: open for extension, closed for modification.

Command Pattern: Undo/Redo Implementation

Analyze
Bloom evidence: Requires analyzing undo implementation, identifying operation types needing different approaches, and diagnosing redo capability problems
code
interface Command {
    void execute();
    void undo();
}

class MoveCommand implements Command {
    private Shape shape;
    private int deltaX, deltaY;
    
    public void execute() {
        shape.move(deltaX, deltaY);
    }
    
    public void undo() {
        shape.move(-deltaX, -deltaY);
    }
}

class CommandManager {
    private Stack<Command> history = new Stack<>();
    
    public void executeCommand(Command cmd) {
        cmd.execute();
        history.push(cmd);
    }
    
    public void undo() {
        if (!history.isEmpty())
            history.pop().undo();
    }
}
activity

Activity: Analyze: Undo Implementation Trade-offs

Speaker notes

This code shows reversible undo—MoveCommand inverts its operation. Students must analyze limitations: works for symmetric operations but not destructive ones like delete (needs Memento for state capture). Critical insight: current design loses redo capability when new commands execute after undo. They should identify need for second stack or position pointer in history. This analysis prepares them for the design exercise on slide 12 where they'll apply these insights to complex scenarios. Discuss solutions emphasizing when to choose reversible commands versus state snapshots based on operation characteristics.

Visitor Pattern: Analyze & Extend

Analyze
Bloom evidence: Students trace double dispatch execution, analyze what changes when extending with new elements vs operations, and evaluate OCP violations
code
interface Expression { void accept(Visitor v); }

class Number implements Expression {
    int value;
    public void accept(Visitor v) { v.visit(this); }
}

class Addition implements Expression {
    Expression left, right;
    public void accept(Visitor v) { v.visit(this); }
}

interface Visitor {
    void visit(Number n);
    void visit(Addition a);
}

class EvaluatorVisitor implements Visitor {
    private Stack<Integer> stack = new Stack<>();
    public void visit(Number n) { stack.push(n.value); }
    public void visit(Addition a) {
        a.left.accept(this); a.right.accept(this);
        stack.push(stack.pop() + stack.pop());
    }
}
activity

Activity: Pattern Analysis & Extension

Speaker notes

This analyze-level exercise makes students trace double dispatch execution to understand the mechanism, then evaluate Visitor's asymmetric extensibility. Adding Multiplication breaks all visitors—violates OCP for operations. Adding PrintVisitor only adds one class—maintains OCP for elements. This asymmetry is Visitor's defining characteristic and critical for pattern selection. Students must recognize that Visitor optimizes for operation extension at the cost of element extension difficulty. This analysis prepares them to evaluate when Visitor is appropriate on slide 15.

Template Method Pattern

Apply
Bloom evidence: Students design Template Method for ReportGenerator, distinguish primitives from hooks, and implement concrete subclasses with justification
text

**Intent:** Define algorithm skeleton in base class, deferring specific steps to subclasses. **Structure:** Template method (final) calls primitive operations (abstract—must implement) and hooks (concrete—optional override). **Hollywood Principle:** Framework calls your code, not vice versa.

code
abstract class DataProcessor {
    public final void process() {  // Template
        readData();
        if (isValid()) { parseData(); transformData(); saveData(); }
    }
    protected abstract void readData();    // Primitive
    protected abstract void parseData();
    protected abstract void saveData();
    protected void transformData() { }     // Hook
    protected boolean isValid() { return true; }
}

Pattern Selection and Best Practices

Evaluate
Bloom evidence: Students evaluate pattern selection for three scenarios, justify choices using SOLID principles, identify patterns to avoid, and assess trade-offs considering maintenance costs
text

**Selection Criteria:** Choose patterns when complexity justifies abstraction. **Key Questions:** Does the problem recur? Will requirements change? Does the pattern reduce coupling? **Anti-Patterns:** Pattern abuse, premature optimization, over-engineering. **YAGNI Principle:** Implement patterns when needed, not speculatively. **Documentation:** Record pattern choice rationale—the 'why' matters as much as 'how'.
