Structuring Large-Scale Programs

Speaker notes

Welcome to Lecture 7 on Software Architecture. Today we shift from detailed design to strategic, system-wide thinking. This lecture is foundational for building maintainable, scalable systems. Emphasize that architecture decisions are costly to change, so getting them right early matters. Set expectations: we'll cover layering, components, dependencies, packaging, and complexity management.

        Module Dependencies & Analysis

        Analyze
        Bloom evidence: Students draw dependency graph, identify cycles, calculate coupling metrics, and propose refactoring to break cycles—analyzing dependency structure and diagnosing problems
        bullets
        • Compile-time, runtime, data dependencies
        • Dependency graphs reveal structure
        • Cyclic dependencies prevent independent deployment
        • Coupling metrics: afferent (incoming) & efferent (outgoing)
        activity

        Activity: Dependency Analysis Challenge

        Instructions: Given: A system with modules Auth, Orders, Payments, Inventory, Notifications. Dependencies: Auth→Notifications, Orders→Auth, Orders→Inventory, Orders→Payments, Payments→Notifications, Inventory→Orders (cycle!), Notifications→Auth (cycle!). 1. Draw the dependency graph and identify all cycles. 2. Calculate efferent coupling for Orders module. 3. Propose refactoring to break cycles using dependency inversion or events.

        Speaker notes

        Dependencies are the 'wiring' of architecture. Types: compile-time (imports), runtime (dynamic loading), data (shared schemas). Dependency graphs visualize relationships. Cycles create tight coupling—can't test or deploy independently. Metrics: afferent (how many depend on you), efferent (how many you depend on). The activity addresses the analyze-level dependency management objective. Students must analyze a real graph, identify problematic cycles (Inventory→Orders→Inventory and Notifications→Auth→Notifications), calculate coupling, and propose solutions like introducing interfaces or event-driven decoupling. Debrief: Orders has efferent coupling of 3. Break cycles by having Inventory depend on IOrderEvents interface or use messaging.

        Slide 13 · content

        Managing Dependencies: Key Principles

        Understand
        Bloom evidence: Presentation of ADP, SDP, SAP principles with explanations and examples—conceptual understanding of dependency management principles without application activity
        bullets
        • Acyclic Dependencies Principle (ADP)
        • Stable Dependencies Principle (SDP)
        • Stable Abstractions Principle (SAP)
        • Break cycles: inversion, interfaces, events
        Speaker notes

        Three key principles for managing dependencies. ADP: No cycles in dependency graph—ensures clean structure. SDP: Depend in the direction of stability—don't depend on volatile modules. Stable modules are hard to change (many depend on them), so they should be dependable. SAP: Stable modules should be abstract (interfaces/base classes)—this allows flexibility. Concrete implementations should be unstable (easy to change). Techniques to break cycles: dependency inversion (introduce interface), merge packages if they're cohesive, use events/observers for decoupling. Example: UI shouldn't depend on specific business logic—use interfaces.

        activity

        Activity: Apply: Reorganize Package Structure

        Speaker notes

        Package organization strategies reflect architectural thinking. Package by layer groups technically (all controllers together)—simple but hides business domain. Package by feature groups by business capability—better for feature teams and domain understanding. Package by component groups architectural units. Screaming architecture means structure reveals what system does, not what framework it uses. The activity applies these concepts: students reorganize a poorly structured codebase, practicing CCP (classes changing together) and CRP (classes used together). They must justify grouping decisions, connecting strategy choice to maintainability goals. This bridges understanding strategies to applying them for real organization problems.

        Slide 15 · content

        Package Principles

        Apply
        Bloom evidence: Students analyze package structure for principle violations (CCP, CRP, ADP), identify specific violations, and propose refactoring moves with principle-based justification—applying package cohesion principles diagnostically
        bullets
        • Common Closure Principle (CCP): change together → package together
        • Common Reuse Principle (CRP): use together → package together
        • Release Reuse Equivalency (REP): reuse granularity = release granularity
        • Acyclic Dependencies Principle (ADP): no cycles in package dependency graph
        activity

        Activity: Apply: Evaluate Package Structure

        Speaker notes

        Package cohesion principles guide organization decisions. CCP minimizes ripple effects by co-locating classes that change for the same reasons. CRP ensures you don't depend on things you don't use by packaging classes used together. REP means packages should be versioned and released as units matching reuse boundaries. ADP prevents circular dependencies that complicate builds and testing. These principles balance competing forces. The activity requires students to apply principles diagnostically: analyze a concrete package structure, identify which principles are violated, and propose refactoring moves. This bridges understanding principles to applying them for real architectural decisions, directly supporting the package organization objective at apply level.

        Managing Complexity

        Apply
        Bloom evidence: Students decompose complex 450-line class, define interfaces using information hiding, calculate complexity metrics, and justify maintainability improvements—applying decomposition and abstraction techniques
        bullets
        • Essential vs. accidental complexity
        • Complexity drivers: size, dependencies, state, distribution
        • Management techniques: abstraction, decomposition, modularity, information hiding
        activity

        Activity: Apply: Simplify Complex Component

        Speaker notes

        Complexity is the enemy of maintainability. Essential complexity comes from problem domain requirements; accidental complexity from poor design choices. Drivers include system size, tangled dependencies, mutable state, and distribution. Management techniques: abstraction hides details, decomposition breaks problems into smaller pieces, modularity creates independent units, information hiding minimizes exposed internals. The activity requires applying these techniques to a realistic complex component. Students must decompose responsibilities, design clean interfaces, and measure improvement using concrete metrics. This directly addresses the complexity management objective at apply level, moving beyond conceptual understanding to hands-on simplification of complex systems.
