Extendibility: Embracing Change

Understand
Bloom evidence: Slide presents definitions and diagrams explaining extendibility concept with modular vs. tangled architecture comparison. No activity requiring higher-order thinking.
heading

Extendibility

bullets
  • Ease of adapting to specification changes
  • Change is inevitable in software
  • Modular design and separation of concerns
  • Localized changes vs. ripple effects
  • Design for change from day one
diagram

Prompt: Side-by-side comparison showing two system architectures. Left side (Good): modular boxes with one highlighted in red showing localized change, other modules unaffected. Right side (Poor): tangled web of dependencies with one change in red causing ripple effects (shown in orange) throughout system. Label: 'Well-designed vs. Poorly-designed System Response to Change'

Speaker notes

Emphasize that requirements always change - new features, regulatory updates, business pivots. Example: e-commerce system adding cryptocurrency payment without restructuring entire checkout. Good design localizes changes: adding new payment method shouldn't require modifying inventory management. Mention the Open-Closed Principle preview: open for extension, closed for modification. Poor extendibility leads to maintenance nightmares and eventual system rewrites. Object-oriented mechanisms like inheritance and polymorphism support extendibility.

Reusability

bullets
  • Using software elements across multiple applications
  • Economic benefits: reduced time and cost
  • Libraries, frameworks, and components
  • Trade-off: generality vs. specificity
  • Requires upfront design investment

Speaker notes

Highlight economic impact: reusable components dramatically reduce development time. Example: standard library collections (List, Set, Map) used in millions of applications - imagine if every project reimplemented these! Discuss the reusability spectrum: highly general (math libraries) to domain-specific (authentication modules) to application-specific. Note the paradox: making something reusable requires more effort upfront (generalization, documentation, testing) but pays dividends across projects. Object-oriented features like inheritance and generics enable reusability.

Classes: Blueprints for Objects

Understand
Bloom evidence: Slide presents class definition with UML diagram showing BANK_ACCOUNT structure. Content explains concept but does not require higher-order cognitive engagement.
heading

Classes

bullets
  • Template defining structure and behavior
  • Attributes (data) and methods (operations)
  • Class as a type in the type system
  • Abstract data type with hidden implementation
  • Unit of modularity and reuse
diagram

Prompt: UML class diagram showing BANK_ACCOUNT class. Top section: class name 'BANK_ACCOUNT'. Middle section (attributes): '- balance: REAL', '- account_number: STRING'. Bottom section (methods): '+ deposit(amount: REAL)', '+ withdraw(amount: REAL)', '+ get_balance(): REAL'. Use standard UML notation with minus for private, plus for public.

Speaker notes

Introduce class as fundamental OO concept: a blueprint or template. Analogy: architectural blueprint defines structure of houses, class defines structure of objects. Class contains attributes (data, state) and methods (operations, behavior). Example: BANK_ACCOUNT class defines what it means to be a bank account - every account has balance and account number, supports deposit and withdraw. Class is also a type: variables can be declared of class type. Emphasize that class is abstract - it's a definition, not a concrete entity (that's an object).

Objects: Runtime Instances

Understand
Bloom evidence: Slide presents object definition with diagram showing three BANK_ACCOUNT instances. Content explains class-object relationship but remains at comprehension level.
heading

Objects

bullets
  • Runtime instance of a class
  • Each object has unique identity
  • Object state: current attribute values
  • Lifecycle: creation, use, destruction
  • Multiple objects from same class
diagram

Prompt: Object diagram showing three BANK_ACCOUNT instances. Top: BANK_ACCOUNT class box. Below, three object boxes connected to class with dashed arrows: 'alice_account' (balance: 1000.0, account_number: 'A001'), 'bob_account' (balance: 2500.0, account_number: 'B002'), 'carol_account' (balance: 500.0, account_number: 'C003'). Label: 'Class and its Instances'

Speaker notes

Distinguish class (abstract template) from object (concrete instance). Analogy: blueprint vs. actual houses built from it. Each object has identity (alice_account ≠ bob_account even if they have same balance), state (current values of all attributes), and behavior (responds to method calls). Objects are created at runtime, exist in memory, and eventually destroyed. Multiple objects can be created from same class, each with different state. Example: three bank accounts for Alice, Bob, Carol - all instances of BANK_ACCOUNT but with different balances and account numbers.

Slide 13 · split

Encapsulation: Information Hiding

Understand
Bloom evidence: Slide presents encapsulation definition with conceptual diagram of public interface vs. private implementation. Explanatory content without application or analysis.
heading

Encapsulation

bullets
  • Bundling data with operations
  • Separating interface from implementation
  • Public interface vs. private details
  • Access control: public, private, protected
  • Benefits: reduced coupling, easier maintenance
diagram

Prompt: Conceptual diagram of an object as a circle with thick boundary. Inside (private): 'balance: 1000.0', 'internal_state', 'implementation details'. Outside boundary (public interface): arrows pointing to 'deposit()', 'withdraw()', 'get_balance()'. External clients shown as small boxes outside, accessing only through public interface. Label: 'Encapsulation Boundary'

Speaker notes

Encapsulation is crucial for quality: it's the mechanism that enables extendibility and reusability. Two aspects: (1) bundling data with operations that manipulate it, (2) hiding implementation details. Example: BANK_ACCOUNT balance is private - clients can't directly modify it, must use deposit/withdraw methods. This enforces invariants (balance never goes negative) and allows implementation changes (store balance in cents vs. dollars) without affecting clients. Analogy: car dashboard (public interface) vs. engine internals (private implementation). Encapsulation reduces coupling between components.

Eiffel Class Structure

Create
Bloom evidence: Activity requires designing complete CIRCLE class from scratch, making decisions about public/private features, preconditions, and quality trade-offs with design rationale.
code
class POINT
create make
feature {NONE} -- Initialization
    make (a_x, a_y: REAL)
        do
            x := a_x
            y := a_y
        end
feature -- Access
    x: REAL
    y: REAL
feature -- Measurement
    distance_to (other: POINT): REAL
        do
            Result := sqrt((x - other.x)^2 + (y - other.y)^2)
        end
end

Walk through POINT syntax: class/create clauses, feature grouping, attributes versus methods, Result keyword, assignment operator. Emphasize feature {NONE} for private initialization. Slide 16 · split

Eiffel Example: BANK_ACCOUNT

Analyze
Bloom evidence: Activity requires analyzing encapsulation rationale (why balance is private) and applying by extending with overdraft functionality, including precondition modifications.
code
class BANK_ACCOUNT
create make
feature {NONE} -- Initialization
    make (a_account_number: STRING)
        do
            account_number := a_account_number
            balance := 0.0
        end
feature {NONE} -- Implementation
    balance: REAL  -- Private
feature -- Access
    account_number: STRING
    get_balance: REAL
        do Result := balance end
feature -- Operations
    deposit (amount: REAL)
        require amount > 0
        do balance := balance + amount end
    withdraw (amount: REAL)
        require
            amount > 0
            amount <= balance
        do balance := balance - amount end
end
activity

Activity: Analyze & Extend: Overdraft Protection

Instructions: 1) Analyze: Why is balance private while account_number is public? What quality attributes does this support? 2) Apply: Sketch how to add overdraft_limit feature and modify withdraw to allow overdrafts up to the limit. Which feature clause? What precondition changes? 3) Share one design decision with a neighbor.

Speaker notes

Walk through encapsulation: balance is feature {NONE} (private), enforcing information hiding. Public interface: get_balance (query), deposit/withdraw (commands). Highlight require clauses as Design by Contract preview—preconditions enforce correctness. Launch activity: students first analyze design rationale (why this encapsulation?), then apply by extending functionality. This combines analytical thinking with practical application. During debrief, emphasize that overdraft_limit should be private, withdraw precondition becomes 'amount <= balance + overdraft_limit', supporting extendibility without breaking encapsulation. Collect solutions showing different approaches to initialization and validation.
