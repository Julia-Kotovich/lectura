The Problem: Code Duplication

Understand
Bloom evidence: Presents problem context explaining why duplication occurs and its consequences—building understanding of motivation for genericity.
bullets
  • Separate class for each type (IntStack, StringStack, PersonStack)
  • Identical logic duplicated across implementations
  • Maintenance nightmare: fix bugs in multiple places
  • Violates DRY (Don't Repeat Yourself) principle
diagram

Prompt: Side-by-side comparison showing two classes: IntStack with push(int), pop():int methods and StringStack with push(String), pop():String methods. Highlight the identical structure with arrows showing duplication. Use contrasting colors to emphasize the only difference is the type.

Speaker notes

Imagine implementing a stack for integers, then realizing you need one for strings, then for custom objects. Without generics, you'd copy-paste the entire implementation, changing only the type. This leads to maintenance nightmares—fix a bug once, you have to fix it everywhere.

Slide 06 · split

Type Instantiation

Understand
Bloom evidence: Explains instantiation syntax and type safety with code examples—primarily understanding how instantiation works, no higher-order task.
bullets
  • Provide actual type arguments when creating instances
  • Type inference reduces verbosity
  • Compile-time type safety guaranteed
  • Each instantiation is a distinct type
code
-- Explicit type instantiation
int_stack: STACK[INTEGER]
create int_stack.make

string_stack: STACK[STRING]
create string_stack.make

-- These are distinct types
int_stack.push(42)        -- OK
string_stack.push("hello") -- OK
int_stack.push("error")   -- Compile error!
Speaker notes

When creating instances, we specify the actual type. STACK[INTEGER] and STACK[STRING] are distinct types—the compiler won't let you mix them up. This is type safety in action: errors caught at compile time, not runtime.

Activity: Evaluate: Constraint Trade-offs

Speaker notes

This evaluation task requires students to analyze trade-offs between constraint designs rather than just applying rules. Approach A is simpler but forces G to be comparable. Approach B is more flexible but more complex. Strong answers recognize that approach B enables priority queues over non-comparable types (like tasks prioritized by external rules). The best solution might combine both: allow optional priority function with COMPARABLE as fallback. This develops judgment in constraint design—a key skill for creating reusable components.
